# JPEG 处理方式

在视频面板选择“直通”时，采集卡 JPEG 原样发送，算法、质量、黑白和编码表设置都不生效。选择“JPEG 压缩”后可以自行选择算法；保存后对后续帧生效，不重新打开采集卡。

| 算法 | 用途与行为 |
| --- | --- |
| 屏幕优化（默认） | 识别完整纯色块，跳过 DCT/量化；与标准高速使用相同参数时，输出 JPEG 字节一致。适合终端和桌面。 |
| 标准高速 | libjpeg-turbo 标准整数编解码，便于一般使用和对照。 |
| 兼容编码 | 便携 Rust 重编码，速度可能较慢，适合兼容性排查。 |
| 整数向量优化 | 使用经过差分验证的 Rust 整数内核；相同参数下保持兼容编码的输出。ARM64 可用 NEON。 |
| 系数重压缩 | 直接重新量化 JPEG 系数，保留源采样并避免解码成 RGB。只降低精度；相同质量数值不等于其他算法的相同码率。格式不适用时回退屏幕重编码。 |
| 保真省流 | 保留源量化表和系数，只优化 Huffman 编码；质量滑块不生效。彩色时不增加二次画质损失；开启黑白会删除色彩分量。只支持常见 8 位 YCbCr/灰度 JPEG，不支持时返回错误，可改选标准或兼容编码。 |

“黑白省流”默认关闭，所有压缩算法均可选。原生算法使用 JPEG 亮度，兼容/整数向量方式从 RGB 转灰度，两者亮度可能略有不同。颜色提示、彩色日志和告警将失去颜色区分。

“优化编码表”不改变所选算法的重建画面，但会多做一次统计；可能减小文件，也可能增加耗时。保真省流始终启用该操作。稀疏终端通常比满屏文字收益更大，具体速度和体积应按实际画面选择。

像素重编码保持 4:4:4 色度；系数方式保留采集卡原有采样。若采集卡已经输出合适的 JPEG，直通通常最省 CPU；较高质量值不保证重新压缩后的画面更贴近已有 JPEG。

配置示例（省略其他已有字段）：

```json
{
  "video": {
    "encoding": "transcode_jpeg",
    "jpeg_backend": "screen",
    "jpeg_quality": 81,
    "jpeg_grayscale": false,
    "jpeg_optimize_huffman": false
  }
}
```

`jpeg_backend` 的合法值为 `screen`、`standard`、`compatible`、`rust_optimized`、`coefficient`、`preserve`。旧配置未提供新字段时，使用 `screen`，黑白和编码表优化默认关闭；已有分辨率、帧率、设备和传输方式保持原值。

坏帧会返回错误并被采集循环跳过，避免单帧解码错误退出服务。输入上限 32 MiB、单边 8192、总像素 33,177,600，输出上限 64 MiB；过大或损坏帧不继续处理。内嵌的 libjpeg-turbo 版本和来源固定在 [原生组件](../components/wingman-jpeg-native/THIRD_PARTY.md)，不替换操作系统的共享库。
