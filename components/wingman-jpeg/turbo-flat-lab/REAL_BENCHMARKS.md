# 真实 HDMI / Linux TTY：性能、画质与码率

2026-11-03，RK3399 真机。按用户后续选择，本轮完成真实 TTY；PVE 没有图形桌面、暂无其他桌面 HDMI 信号源，**没有桌面测试结果**。

实测支持 TTY 是纯色块快捷路径的有效场景：保持输出 JPEG 字节完全一致时，编码阶段耗时减少 **27%～42%**；包括解码的整帧重压缩减少 **18%～31%**。系数域路径在选取近等码率工作点后，整帧耗时减少 **31%～50%**，文字指标总体接近，但输出不是同一个 JPEG。

## 输入与方法

- 信号源为真实 PVE Linux 内核 TTY1，逻辑终端 174×49 字符，HDMI 输出经正在使用的采集卡输入 RK3399 的 `/dev/video5`。原始数据是 1920×1080、8 位 sequential YCbCr、4:2:2 MJPEG，协商 30 FPS。
- 三种画面：已有稀疏命令提示符；实际 `ls -l --color=never /usr/bin` 输出；实际 `ls -C --color=always /usr/bin` 输出。后两者通过 SSH 执行命令，将结果写入现有内核 TTY，由真实字体和显卡输出，经 HDMI 采集；没有以生成的 JPEG/网页代替这些样本。
- 每种画面抓取 5 次，只有光标闪烁等静态差异，按 SHA-256 去重后每组 2 帧、共 6 种不同内容，**不是 15 种独立工作负载**。完整采集元数据和哈希已归档。
- 仅只读访问服务进程中明确属于 `/dev/video5` 的 mmap 区域；两次读取间隔 40 ms、数据一致才保存。扫描 JPEG 标记边界，并由实际解码器检查无警告。没有重新打开采集队列、停止进程、重启服务或改变采集配置。这不提供曝光时刻或端到端延迟测量。
- 在 CPU 4 大核上以 `nice -n 10 taskset -c 4` 顺序运行，保持原 ondemand governor，背景服务继续运行。C 两库均为官方 libjpeg-turbo 2.1.5、GCC 9.2.0、Release/SIMD、静态 musl，相同编译设置；只修改其中一库的纯色块路径。每个程序同进程轮换执行模式。
- 主性能表：2 轮预热、21 轮计时，报告中位数；P95 在原始日志。质量扫描的 15 个质量请求各只计时 1 轮，**这些单轮时间不用于性能结论**；近等码率选定点另做 21 轮测量。Rust 路径为 2 轮预热、11 轮计时。
- 全部码率为 `JPEG字节数 × 8 × 24 / 1,000,000` 的固定 24 FPS 有效载荷折算，不是公网实测码率；不含 HTTP/TCP/TLS 开销，也不表示当前服务实际输出达到 24 FPS。

## 1. 保持输出字节完全一致的系统库补丁

主表采用质量 81、**4:4:4**，与当前分支保留文字色度精度的编码设置一致。包含读取原始 JPEG、RGB 解码、编码、对象创建销毁；不含设备等待、网络和浏览器。

| 真实画面 | 可用纯色分量块 | 原版整帧 | 补丁整帧 | 整帧耗时变化 | 原版→补丁编码阶段 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 稀疏 TTY | 99.58% | 54.94 ms | 37.90 ms | −31.0% | 40.35→23.46 ms（−41.9%） |
| 满屏单色列表 | 93.20% | 61.22 ms | 46.28 ms | −24.4% | 42.43→27.63 ms（−34.9%） |
| 满屏彩色列表 | 73.51% | 66.06 ms | 54.31 ms | −17.8% | 45.20→33.17 ms（−26.6%） |

每轮完整 JPEG 字节比较通过。**码率和画质没有变化，收益是省 CPU。** 比例按 Y/Cb/Cr 的分量块计数，不等于屏幕面积；单色列表的自适应路径实际使用了约 92.51% 的块，少量纯色块因 cooldown 留在原路径。

还保持源 **4:2:2** 重测了每组的两种不同帧：原版/补丁的整帧中位数约为 43.5～44.5 / 32.3～32.8 ms、49.9 / 40.4～40.6 ms、53.9～54.5 / 46.4～46.9 ms，分别减少约 26%、19%、14%。分量数不同，不能把两个采样设置的耗时直接归为内核提升。

## 2. 高质量请求下，重复压缩经常没有必要

采集卡已有自定义量化表（亮度 DC=8、色度 DC=1），不能把它简单视作标准“质量 75”。在质量请求 81 下，系数路径有 **122/128** 个量化项会被 coarsening-only 规则限制为源值，只有 5 项发生变化。它与 RGB 路径的有效量化表不同，不能仅凭相同的 `81` 宣称相同质量条件。

下面以采集卡原始 JPEG 解码的 RGB 为参考。系数路径保留源 4:2:2；RGB 重编码为主表的 4:4:4。

| 画面 | RGB q81 码率 | 系数 q81 码率 / 耗时 | 原始帧直接透传码率 | RGB / 系数文字区域 PSNR |
| --- | ---: | ---: | ---: | ---: |
| 稀疏 TTY | 13.52 Mbps | 10.20 Mbps / 20.35 ms | 10.19 Mbps | 31.99 / 71.14 dB |
| 满屏单色 | 50.83 Mbps | 44.28 Mbps / 32.51 ms | 44.28 Mbps | 31.90 / ∞ dB |
| 满屏彩色 | 75.14 Mbps | 62.94 Mbps / 35.99 ms | 64.22 Mbps | 28.93 / 43.88 dB |

系数标量与 NEON 的 JPEG 字节一致，但与 RGB 路径不相同。这里的 ∞ 只表示该帧的解码像素一致，不能推广为降质量操作无损。直接透传则原始 JPEG 字节一致，不增加二次损失；原始 HDMI 已经在采集卡上经过有损 JPEG 编码。

透传测试仅预留缓冲并复制 53～335 KB，耗时约 0.015～0.085 ms。它是**复制成本**，不包括分配、采集等待、网络或显示，不能把它解释为整个视频链路只有这么多延迟。就这些质量 81 样本，若原始码率可接受，省去重压缩比继续优化编码器更有价值。

## 3. 近等码率下比较画质与速度

为避免“系数路径更清晰，但偷偷用了更多字节”，对照源 4:2:2 的 RGB 路径选取了以下实测点。码率差异均小于 0.15%，两个路径仍是不同算法和输出。

| 画面 | RGB / 系数质量请求 | RGB / 系数码率 | RGB / 系数整帧耗时 | RGB / 系数文字 PSNR | RGB / 系数文字 SSIM |
| --- | ---: | ---: | ---: | ---: | ---: |
| 稀疏 TTY | 35 / 35 | 9.205 / 9.209 Mbps | 43.22 / 21.64 ms | 20.23 / 20.44 dB | 0.9520 / 0.9568 |
| 满屏单色 | 35 / 35 | 28.478 / 28.518 Mbps | 48.73 / 29.44 ms | 20.26 / 20.45 dB | 0.9520 / 0.9565 |
| 满屏彩色 | 50 / 44 | 38.563 / 38.548 Mbps | 52.28 / 35.98 ms | 20.35 / 20.24 dB | 0.9560 / 0.9572 |

这组工作点中，系数路径耗时分别减少约 **50%、40%、31%**。文字指标总体接近；彩色帧的文字 PSNR 略差、SSIM 略好，没有全面质量胜出。

尤其不能沿用合成图“系数输出只大 4%～10%”的范围：真实彩色 TTY 在同为 q50 时，RGB 为 200,847 字节，系数为 277,797 字节，**多约 38%**。上表因此调整到系数 q44，而不是把更大文件的画质直接当作算法优势。

全量质量请求：30、32、35、36、38、40、42、44、46、48、50、65、75、81、90。由于源图已经量化，重压缩的体积和相对源图的 PSNR 存在离散变化；更高质量请求不保证更贴近已压缩的源帧。这里是选定工作点的比较，不宣称连续码率曲线或全局最优率失真性能。

### 画质度量

PSNR 的参考为**采集卡原始 JPEG 的解码像素**，不是未压缩 HDMI 真值。大面积黑色会抬高整图分数，因此额外计算文字区域：任意 RGB 通道大于 32 的像素，向外扩展一像素，包含字体边缘与附近振铃。

文字 PSNR 为该掩码内三通道误差；SSIM 使用 RGB 的 BT.709 权重亮度、11×11 高斯窗口、sigma=1.5、总体协方差，文字 SSIM 取对应局部图均值，去除图像边界 5 像素。稀疏/单色/彩色的掩码分别约占 0.47%、6.90%、10.36%。它是明确规定的 TTY 指标，不代替 OCR、主观可读性或桌面图片测试。

Python 质量分析的解码器版本与 C 构建不同，因此同时保留 C 的整图 PSNR 和 Python 的整图/文字指标，不混作同一数值。空 PSNR JSON 值代表正无穷，另有像素一致标志。

## 4. 系统库已有的 Huffman 优化：收益依赖画面

另用库已有的 `optimize_coding=TRUE`，保留**全部源量化表和系数**，只重写熵编码。benchmark 中请求 q100 再由 coarsening-only 规则取源表，`changed_quantizers=0`；不是把源画质提升到 100。零表变化时整个重新量化循环跳过。这项配置不是本项目发明的算法。

| 画面 | 原始字节→优化 Huffman 字节 | 体积变化 | 优化后码率 | 处理耗时 |
| --- | ---: | ---: | ---: | ---: |
| 稀疏 TTY | 53,084→30,478 | −42.6% | 5.85 Mbps | 29.92 ms |
| 满屏单色 | 230,626→216,658 | −6.1% | 41.60 Mbps | 44.25 ms |
| 满屏彩色 | 334,500→319,877 | −4.4% | 61.42 Mbps | 52.27 ms |

三种输出解码像素与源帧完全一致。稀疏 TTY 有用，但满屏情况下节省较少，统计/重新编码的成本相对明显；它不是普遍更快的方案，更适合按带宽和画面结构选择。

## 5. Rust 处理路径模型

同一实际输入，还重新运行了四种 Rust 模型，均为质量 81、4:4:4、ThinLTO、单 codegen unit，复用输出容量。它重现相关函数的处理路线，**没有在运行中服务内打点**；线上逐帧分配和其他开销不完全一致。

| 输入 | 旧 image 路径模型 | 当前分支 jpeg-encoder | 上阶段组件 NEON | Rust 核心实验 |
| --- | ---: | ---: | ---: | ---: |
| 稀疏 TTY | 128.25 ms | 124.11 ms | 95.78 ms | 74.39 ms |
| 满屏单色 | 144.78 ms | 135.64 ms | 107.87 ms | 87.56 ms |
| 满屏彩色 | 157.54 ms | 143.63 ms | 116.16 ms | 100.43 ms |

后三种的 JPEG 字节相同；旧 image 路径与其不同。数据说明既有 Rust 核心优化有效，但完整处理仍明显慢于成熟 C 库。这些编码、解码及分配路线一起改变，不能把 C/Rust 差距全部归因于 DCT。

代码提交 `cbc3b4c` 加入真实帧工具；最终源码、原始日志和图表均保留。原始日志和二进制哈希：[rk3399-real-tty.json](benchmarks/rk3399-real-tty.json)；全部画质/体积/耗时记录及分析库版本：[rk3399-real-quality.json](benchmarks/rk3399-real-quality.json)。采集图片和放大裁剪位于本地忽略的 `output/playwright/jpeg-real-2026-11-03/`，**未加入 Git 或上传到编译服务器**。

实际验证：C 两版本以 `-O3 -static -Wall -Wextra -Werror` 编译退出 0；Rust `cargo build --locked --release --target aarch64-unknown-linux-musl --example real_capture` 退出 0；相同目标 Clippy 退出 0，沿用四类上游风格豁免（`manual_is_multiple_of`、`chunks_exact_to_as_chunks`、`clone_on_copy`、`needless_borrow`）。JPEG 边界测试 3 个方法、9 个子用例通过，15 张实际帧通过最终边界解析，6 种不同帧经 C 解码无警告。所有真实帧 benchmark 的 JPEG 字节对照通过；分析成功写出 347 行结果，去重后 117 组编码/参考图质量测量。

主表来自最终默认二进制；早期重复测量和质量扫描的二进制也各自保存哈希。最终版本加入零量化变化跳过和 Huffman 编译开关；默认 q81 保存的五种输出逐字节核对早期版本一致，近等码率点也与对应扫描结果一致。
