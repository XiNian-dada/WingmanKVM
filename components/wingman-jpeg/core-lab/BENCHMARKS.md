# RK3399：Rust 内核实验结果

2026-11-03，在实际 RK3399 上运行，绑定 CPU 4（大核，最高 1.8 GHz），`nice -n 10`，未修改 governor。后台 WingmanKVM 服务继续运行，故这是共享机器测量，不是独占实验室环境。原始日志及二进制 SHA-256 在 [benchmarks/rk3399-final.json](benchmarks/rk3399-final.json)。

1920×1080 RGB，质量 81，4:4:4，标准 Huffman，准确整数 DCT；仅测 RGB→JPEG，**不含采集、JPEG 解码、网络或浏览器延迟**。Rust 同一二进制中轮换各模式，1 轮预热、15 轮计时；最终 release 为 ThinLTO、单 codegen unit。系统库参考在同一个大核另行运行，编译器、语言和分配实现不同，不能归因于某条指令。所有输出缓冲均预留复用。

| 合成输入 | 未修改上游核心 | 上阶段组件 | 本次全部优化 | 系统 libjpeg-turbo 2.1.5 |
| --- | ---: | ---: | ---: | ---: |
| 纯色 flat | 85.947 ms | 84.968 ms | 33.863 ms | 37.471 ms |
| 稀疏终端 sparse | 88.419 ms | 87.207 ms | 38.588 ms | 39.344 ms |
| 密集字符 desktop | 104.353 ms | 102.417 ms | 70.821 ms | 48.374 ms |
| 渐变 gradient | 89.952 ms | 88.775 ms | 65.009 ms | 41.018 ms |
| 噪声 noise | 178.048 ms | 171.074 ms | 153.189 ms | 77.711 ms |

“未修改上游核心”使用 `jpeg-encoder 0.6.1`，与实验共享批量 RGB 输入前端，用于隔离核心算法；不是原版逐像素公共接口的测量。上阶段组件为父目录 `wingman-jpeg`，这次也用相同编译配置重新测量。每轮断言所有 Rust 模式 JPEG 字节相同。C 库的色彩取整及编码细节不同，不能把 C 与 Rust 的输出视作字节相同。

本次 Rust 优化对自身基线有明显帮助，但**没有普遍击败系统库**。纯色场景有优势，稀疏终端基本相当；其余场景仍明显落后，噪声约慢一倍。五种合成图不能代表真实捕获内容分布，也不据此推断整条视频链路提升。

## 消融与正确性

完整九组消融在原始日志中。代表性的内核微基准：随机块 DCT 从 192.898 降至 178.323 ns；纯色块快捷 DCT 为 50.264 ns；量化从 341.661 降至 138.553 ns。主要收益来自量化及跳过可证明不必做的工作，单独重排 DCT 的提升较小。

- ARM64：33 个单元测试、1 个完整 JPEG 差分集成测试通过。包括百万结构化/随机块、256 种纯色及单像素扰动、非对齐加载、截断输入，以及完整 i16 系数域的量化对照。
- 主机：28 个单元测试、1 个集成测试、1 个文档测试通过。
- Rust 1.88：库与 `--no-default-features` 检查通过。
- Clippy 的正确性检查通过；全目标严格检查对四类上游既有风格告警做了命令行豁免：`manual_is_multiple_of`、`chunks_exact_to_as_chunks`、`clone_on_copy`、`needless_borrow`。不宣称无条件零告警。
- `scripts/verify_dct_bounds.py` 的数学模型边界检查通过；它不代替程序测试。

没有接入生产服务、发布包或修改系统库。随后直接优化系统库的实验见相邻的 [turbo-flat-lab](../turbo-flat-lab/README.md)。

真实 HDMI / PVE TTY 的后续测量见 [真实帧报告](../turbo-flat-lab/REAL_BENCHMARKS.md)，包含 `examples/real_capture.rs` 对完整 Rust 处理路线的独立模型比较。合成输入与真实采集 JPEG 的解码、采样及色彩处理不同，不能直接拼接两次测量的耗时。
