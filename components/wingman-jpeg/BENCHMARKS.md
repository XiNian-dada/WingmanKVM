# RK3399 实测：2026-11-03

这是离线 JPEG 处理测试，未连接 V4L2/USB 设备，未改视频服务。测试期间视频服务保持 active，PID 未改变。

## 方法

RK3399 的 CPU4，最高频率 1.8 GHz，进程绑定单核，nice=10；没有修改 CPU 调速器或服务 CPU 亲和性。云端使用 Rust 1.99.1、标准 Cargo release 配置交叉构建 `aarch64-unknown-linux-musl`，二进制在真实板子执行。温度从约 35°C 上升至约 38°C。

三种固定种子的 1920×1080 合成输入：终端式文本图案、渐变、随机噪声。源 JPEG 质量 95、4:2:2；输出质量 81，彩色始终为 4:4:4。每条路径预热一次，再轮换执行顺序，每组 15 个样本。比较发生在同一个二进制、同一进程中，所有路径都允许复用输出 Vec 容量。

“当前”基线为未修改的 `image 0.25.10` 解码 + `jpeg-encoder 0.6.1` 编码，即前一轮 WingmanKVM 的实现。“原始 image”行对应更早的 image 编码实现，其 JPEG 字节不同，不用于相同输出的优化结论。原库的可选 x86 AVX2 特性未启用，与当前项目配置一致；ARM 本来也不使用该特性。

## 中位耗时（ms/帧，越低越好）

| 路径 | 文本图案 | 渐变 | 随机噪声 |
| --- | ---: | ---: | ---: |
| 仅编码：未修改上游 | 120.433 | 107.596 | 175.213 |
| 仅编码：批量行处理 + 标量 | 99.241 | 86.658 | 154.244 |
| 仅编码：批量行处理 + NEON | 98.678 | 85.995 | 153.692 |
| 原始 image 彩色链路 | 188.270 | 144.221 | 317.385 |
| 当前彩色链路 | 186.233 | 148.671 | 293.693 |
| 优化彩色链路（输出字节一致） | 158.061 | 121.223 | 265.190 |
| 当前 RGB 灰度链路 | 121.270 | 88.512 | 193.076 |
| 优化 RGB 灰度链路（输出字节一致） | 109.627 | 76.716 | 181.001 |
| 直接 JPEG 亮度（画面定义不同） | 86.923 | 54.510 | 151.620 |

## 相同输出的收益

| 场景 | 编码耗时减少 | 彩色完整链路耗时减少 | RGB 灰度完整链路耗时减少 |
| --- | ---: | ---: | ---: |
| desktop | 18.1% | 15.1% | 9.6% |
| gradient | 20.1% | 18.5% | 13.3% |
| noise | 12.3% | 9.7% | 6.3% |

**大部分编码收益来自批量行缓冲写入，而不是 NEON 单独贡献。** 在批量标量路径之上，NEON 的额外收益约 0.4%–0.8%。不能把整个 12%–20% 的改善都宣传成 SIMD 收益。DCT、量化、熵编码没有改变。

每轮基准都会断言：上游编码、自有标量、自有 NEON 的 JPEG 字节一致；当前彩色与优化彩色字节一致；当前 RGB 灰度与优化 RGB 灰度字节一致。相同输出的路径尺寸也完全一致，没有通过降低画质、减少颜色采样或改变画面内容换速度。

## 直接 JPEG 亮度的差异

该选项省掉 RGB 输出及 RGB 灰度转换，进一步减少耗时，但不是同样画面的等价优化。JPEG Y 通常使用 BT.601 系数；image 0.25.10 的 RGB 灰度使用 sRGB/BT.709 派生亮度系数，还存在浮点舍入、上采样和色彩裁剪差异。

相对于当前 RGB 灰度输出，直接亮度输出解码后的差异为：

| 场景 | 灰度图 PSNR（dB） | 最大绝对像素差 |
| --- | ---: | ---: |
| desktop | 36.394 | 31 |
| gradient | 26.678 | 42 |
| noise | 25.919 | 86 |

因此 `ColorMode::GrayRgb` 和 `ColorMode::JpegLuma` 在 API 中显式分开，不自动替换。噪声图的最大像素差较大，直接亮度模式适合接受该亮度定义的应用。

## 正确性与构建

- 真实 RK3399 上执行 6 项 release 测试，全部通过。
- 颜色转换遍历全部 16,777,216 种 RGB，NEON 与上游固定点结果完全一致。
- RGB 灰度另遍历全部 16,777,216 种 RGB，与 image 0.25.10 的转换结果完全一致；覆盖 ARM FMA 与 x86 非 FMA 路径。
- 测试包括不对齐输入、0–31 像素尾部、奇数尺寸、质量 1/50/81/100、完整 JPEG 字节比较、渐进 JPEG、灰度源、缓冲复用、错误和大尺寸头部拒绝。
- x86_64 release 测试也全部通过；Rust 1.88 最低版本 check 通过；host 与 AArch64 `cargo clippy --locked --all-targets -- -D warnings` 通过。
- 本组件独立于主项目，主项目目前未引入该依赖，主项目 CI 也尚未自动运行本组件测试。

这些是 CPU 处理耗时，不是键盘到画面的端到端延迟；没有测量真实采集卡内容、长期稳定性或多个并发流。15 样本的 P95 只作为本次小规模试验的描述，不代表长期尾部延迟保证。

## 复现

```sh
cd components/wingman-jpeg
cargo test --locked --release
cargo build --locked --release --example compare
# 在 RK3399 上；根据机器调整 CPU 编号
nice -n 10 taskset -c 4 target/release/examples/compare desktop 15 1920 1080
nice -n 10 taskset -c 4 target/release/examples/compare gradient 15 1920 1080
nice -n 10 taskset -c 4 target/release/examples/compare noise 15 1920 1080
```

交叉构建时使用 `--target aarch64-unknown-linux-musl`，并配置对应链接器；本次使用工具链自带 rust-lld。构建过程完全在云端，板子只执行静态二进制。原始数值、P95、输出大小及二进制 SHA-256 见 [机器可读结果](benchmarks/rk3399-2026-11-03.json)。
